# Helix Storybook — Agent Contract

Storybook is the living, always-in-sync reference for every Helix token and component. See the root
`CLAUDE.md` for the token/component contract itself — this file covers Storybook-specific structure rules.

**A component isn't done until it has a story, and `contracts/manifest.json` knows about it.** Every
`Components/{Name}.stories.tsx` / `Layout/{Name}.stories.tsx` file is expected to exist for every entry in
the manifest — after adding or renaming a story, run `pnpm docs:manifest` from the repo root; a missing
story shows up there as a `drift` entry instead of silently going unnoticed.

**`Changelog.stories.tsx`** (top-level, sidebar position right after "Getting Started" — see `preview.ts`'s `storySort`)
renders `.ai/maps/changelog.json`, generated from `git log` by `pnpm docs:changelog`. It is the project's
only changelog — there is no separate `CHANGELOG.md` to keep in sync. Regenerate it (from the repo root)
when you want the page to reflect commits made since its last run.

**`Status.stories.tsx`** (top-level, right after Changelog) renders `contracts/manifest.json` as a doneness
matrix — every component's status (draft/beta/stable/deprecated, with a legend explaining each), and
whether it has a contract/export/doc/types/story/documented-a11y, plus a Figma column sourced from
`contracts/figma-sync.json` (whether that component is modeled in Figma). Each component name links to its
own docs page. Regenerate the manifest source with `pnpm docs:manifest`.

**`contracts/figma-sync.json`** tracks, per component, whether it's modeled in the Figma file, whether its
variants match the code, and whether its Figma variable bindings match `component.*` tokens — surfaced in
Storybook only as the Status page's Figma column (there is no dedicated Figma Sync story/page; it was
removed as redundant with that column). Unlike `manifest.json`, **this file cannot be regenerated by a
local script** — there's no Figma REST token configured in this repo, so a check can only be run by an
agent with Figma MCP access (`get_metadata` + `get_variable_defs` against the file, compared against the
component's `*.types.ts` and `component.<name>.*` tokens) and the result hand-recorded into the JSON. See
that file's own `howToRefresh` field.

**Standing rule when building a component in Figma that has an icon in its anatomy: use a real instance
from the Figma file's own Icons page, never a placeholder shape.** See `figma-sync.json`'s `iconRule` field
for the exact recipe (`createInstance()` off the matching icon component, resize, then override the
instance's vector stroke to the right `icon/*` color variable). Same standing rule for typography: apply
text via a real named Figma Text Style (`setTextStyleIdAsync`), never a loose `fontSize` variable binding
on its own — see `figma-sync.json`'s `typographyGapFoundAndFixed...` field for why.

## Every story starts with a title + description — no exceptions

**Every `*.stories.tsx` story's rendered output must open with a `StoryHeader`** (title + description),
before any other content. This applies to every story in the app — Foundation, Components, Patterns,
Pages, everything — not just the Foundation token stories it was first built for.

```tsx
import { StoryHeader } from '../_shared/StoryHeader'; // path relative to the story file's location

export const MyStory: Story = {
  render: () => (
    <div>
      <StoryHeader title="Section — Thing" description="One sentence: what this shows and why it matters." />
      {/* ...the actual story content... */}
    </div>
  ),
};
```

- **Import `StoryHeader` from `apps/storybook/stories/_shared/StoryHeader.tsx`** — it's app-wide, not
  Foundation-specific, even though Foundation was the first place it was used.
- **Title format: just the specific name, never repeat the group** — `"Color"`, `"Spacing"`, `"Radius"`,
  not `"Primitives — Color"` or `"Semantic — Radius"`. The group (`Primitives`/`Semantic`/`Theme`/...) is
  already shown by Storybook's own sidebar nesting (from `meta.title: 'Foundation/Primitives'`) and the
  page breadcrumb — repeating it in the header is redundant, not clarifying. Same rule for Component/Pattern
  stories: just the component or pattern name (e.g. `"Button"`, `"Empty State"`), never `"Components —
  Button"`.
- **Description**: one or two sentences — what the story shows and why it matters, not a restatement of
  the title. Reuse existing `parameters.docs.description.story` text where one already exists rather than
  writing a second, different description — and remove the now-redundant `parameters.docs.description`
  entry once the visible header carries the same text, so there's one source of truth, not two.
- **Typography/spacing/font-family is fixed, do not improvise it** — `StoryHeader` matches the
  *actual rendered* Component "Docs" page, verified with computed styles pulled live from a running
  Storybook instance (`localhost:6006`, Badge's docs page, `.sbdocs-title` `h1` and its following `p`)
  via a Playwright inspection script, not read off the `@storybook/blocks` package source or recalled
  from memory:
  - Title (`h1`): `32px` / **`700` (bold)** / line-height `36px` / margin-bottom `16px`
  - Description (`p` — a plain paragraph right after the `h1` on a real docs page, **not** an `h2`;
    the visible `h2` there is the unrelated "Stories" section heading further down): `14px` / `400` /
    line-height `24px` / margin-top `16px` / margin-bottom `16px`
  - Font family: Storybook's own theme stack, `"Nunito Sans", -apple-system, ".SFNSText-Regular",
    "San Francisco", "system-ui", "Segoe UI", "Helvetica Neue", Helvetica, Arial, sans-serif` — the
    docs chrome uses this regardless of Helix's own font tokens, since `StoryHeader` is mimicking that
    chrome's look, not the component library's typography.

  Earlier passes at this spec (both a source-only reverse-engineering pass, and a verbal
  re-description) landed on different, wrong numbers each time — trust a live computed-style
  measurement over either. If this ever drifts again, re-measure the live page rather than
  re-deriving from source or memory. This makes a component's autodocs page and any hand-built
  story's Canvas view look like the same design system, not two different ones. If you need a visually
  different header for a specific story, that's a sign the content doesn't belong in `StoryHeader` —
  don't fork its styling inline.

**Why this exists:** before this rule, `Foundation.stories.tsx`'s sections had no visible header at all —
just token content, with any explanation buried in `parameters.docs.description.story` (only visible in
the separate "Docs" tab, never in "Canvas" view, which is what most people actually look at first).

## Token-driven stories must read from `tokens.json`, not hardcode a list

See `packages/tokens/CLAUDE.md` → "Adding a token" step 6. Where a story enumerates tokens (a color table,
a spacing scale, a list of radii…), prefer importing `tokens.json` directly
(`import tokensJson from '../../../../packages/tokens/src/tokens.json'` — path depth varies by file
location; `resolveJsonModule` is already enabled in `tsconfig.json`) over a hardcoded array of keys.
A derived list picks up a token addition/rename/removal, and its `$description`, on the next build with
zero story edits. `packages/tokens/dist/index.ts` is **not** the right import for this — it only holds
resolved values, dropping both the alias path (`$value`) and `$description`; import from `src/tokens.json`
when you need either of those, from `dist/index.ts` only when you need a plain resolved value at runtime.

## Foundation story structure

`apps/storybook/stories/Foundation/` mirrors the 4-collection structure of the live Figma file, not a
flat list of token categories:

- `Primitives.stories.tsx` — raw, role-agnostic scales. Never what components actually bind to.
- `Semantic.stories.tsx` — the tokens components actually consume. Shows `$description` for every token,
  read directly from `packages/tokens/src/tokens.json` so the visible copy stays in sync with the source.
- `Theme.stories.tsx` — semantic color only, with a working light/dark toggle
  (`document.documentElement.setAttribute('data-theme', ...)`, matching the `:root[data-theme="dark"]`
  selector `packages/tokens/src/build.ts` actually emits).
- `TextStyles.stories.tsx` — the named `{role} / {size} / {weight}` combinations mirroring Figma's Text
  Styles.
- `_shared.tsx` — helpers local to Foundation (`SectionHead`, `SpacingBar`, `DescCaption`, `TokenLeaf`).
  Not a `*.stories.tsx` file, so Storybook's glob doesn't pick it up as its own story.

`packages/tokens/src/tokens.json` is the SSOT for semantic-token descriptions: if a `$description`
changes there, Storybook should reflect it automatically by reading the same JSON, not by adding a
second hardcoded explanation in the story file.

## Component token tabs stay in Components only

The `helixTokens` docs panel is for `Components/*` stories only. Do not add `helixTokens` to Foundation,
Patterns, Pages, or other non-component stories, or the token tab will appear where it does not belong.

A token category that exists in both `primitive.*` and `semantic.*` (color, spacing, shadow, motion) gets
a section in both files. A category with no primitive layer (radius) or no semantic layer at time of
writing gets a short explanatory note in the file where it's missing, rather than silently having no entry
at all — see `Primitives.stories.tsx`'s `Radius` story for the pattern.

## Every component story links to Figma

Every `Components/*` and `Layout/*` story's autodocs page shows a "View in Figma ↗" link, right under the
purpose description — sourced from `contracts/figma-sync.json` by component name, never hand-typed per
story. This is automatic: `createComponentDocsParameters(XDoc)` (`_shared/component-docs.tsx`) looks the
component up in `figma-sync.json` and appends the link to `docs.description.component` when
`inFigma: true`; it renders nothing for a component not yet modeled in Figma, rather than a broken link.
Nothing to do per-component — the link appears automatically the moment `figma-sync.json` marks that
component `inFigma: true`, and disappears just as automatically if that ever flips back to `false`.

`StoryHeader` (`_shared/StoryHeader.tsx`) also accepts an optional `figmaUrl` prop for the same link,
rendered next to the title on the Canvas view — pass it (via the same `figma-sync.json` lookup) on any
story that builds its own custom header instead of going through `createComponentDocsParameters`.
